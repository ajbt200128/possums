# Possums privacy policy and engineering requirements

**Status: engineering policy; not a claim that every control is deployed.** Last researched: 2026-10-07. The reviewed MVP runtime was deployed before the API-only cutover; live evidence and remaining gaps are recorded separately. This API-only policy update is not evidence of a new deployed image. See [`docs/telemetry-plan.md`](docs/telemetry-plan.md) for implementation gates and [`docs/verification.md`](docs/verification.md) for scoped release evidence. This is not yet a complete public legal notice: operator identity, jurisdiction, privacy contact, legal obligations, and support/deletion procedures need review before publication.

## Mandatory reference and change control

Read this file **before touching telemetry**: instrumentation, metrics, logging, tracing, SDK configuration, collectors, resource discovery, dashboards, alerts, exporters, deployment, crash reporting, or diagnostic/support tooling. Link the applicable sections in the change description and verification record. Repository guidance in [`AGENTS.md`](AGENTS.md) requires this review.

This policy applies to real data in **every environment**, including testing. A `test` label is not consent to collect sensitive data. Only an isolated, operator-controlled synthetic workload may use the synthetic-testing exception below. Broader collection requires an explicit policy/threat-model decision first, not a new environment variable or vendor default. If documents disagree, keep the stricter privacy restriction until the conflict is resolved; do not silently weaken `AGENTS.md` or the phase contract.

## MVP deployment and retention decision

On 2026-10-08 the operator approved deploying this work to the existing production gateway without a separate isolated test instance, and accepted Honeycomb's default retention for the MVP. Seven days is now a future retention goal, not an MVP export prerequisite. The initial destination expectation was Honeycomb `dev`. During live verification, the supplied key sent the approved resource metrics to `prod/metrics`; the operator explicitly chose to keep `prod`. Use that confirmed destination without displaying or committing credentials. The Honeycomb environment is a destination/access boundary, not evidence that the source workload is synthetic.

The operator subsequently selected direct authenticated OTLP HTTPS to Honeycomb US, with no Collector sidecar, and automatic runtime enablement when valid allowlisted configuration and ingestion credentials are present. `OTEL_SDK_DISABLED=true` disables export. Missing or invalid configuration fails closed without failing inference. Synthetic fixture mode is test-only, never a production requirement or source label.

The operator also chose a continuously enabled MVP, rejecting bespoke DNS cancellation and a one-second global shutdown guarantee. Use standard DNS and a simple deployment-level disable setting; no live-toggle framework is required. Shutdown drops pending metric batches without flushing partial windows. An already-started system lookup for the fixed Honeycomb hostname may outlive the export attempt; resolver completion time and whole-process exit latency are not guaranteed. This is not permission to detach a task holding credentials or metric payloads and let it continue uploading.

These decisions change deployment authorization, transport topology, enablement, shutdown expectations and metric retention only. They do not authorize content, identifiers, request logs/traces, bypassing the release algorithm, marking real/mixed traffic as isolated synthetic, or claiming that unverified processor properties passed. Production deployment may keep telemetry disabled while the remaining privacy/runtime gates are completed. Record the effective default retention when available; do not claim an exact duration or immediate backup deletion without evidence. Request shorter retention after the MVP; do not create a secondary archive.

## What we are protecting

Our goal is to operate a reliable private inference gateway without building a history of people's activity. Collect the minimum operational information, keep it briefly, and explain the limitations. Do not sell request data, use it for advertising/profiling, or repurpose observability data to train models.

Possums is **not Signal-style end-to-end encrypted messaging**: the gateway and Tinfoil inference service process prompt and response plaintext in memory. Attestation authenticates measured code/configuration and endpoint binding; it does not prove that retention is impossible after runtime compromise. It does not make unrelated services attested or prevent traffic correlation.

The following remain explicit risks: network timing and source-address visibility to network intermediaries, TLS termination, open egress, dependencies, upstream inference caches, live catalog changes outside the gateway measurement, account reuse, and platform/operator access. A future external accounting store can associate payments with accounts and observe reservation/settlement events; it is not anonymous or hardware-verifiable. Persistent accounting would also introduce backup/WAL retention concerns. Phase 0 has manually granted demo credit, not payments or durable purchased-credit accounting.

Local SDK prompt-cache persistence and unintended persistence must be explicitly disabled. The narrow operator-authorized upstream session-prefix reuse above does not authorize a shared environment namespace, cache warming, replay, local prompt files or cache/token/cost telemetry except the narrowly approved five-minute numeric token aggregates below. Cache scopes and provider costs remain prohibited. The opaque random scope is still a sensitive session-linked pseudonym: gateway/inference compromise can expose it and its mapping; shared hit timing can correlate conversations within a session. Fresh logins avoid deliberate namespace linkage but do not prevent network/cache timing correlation. Removing gateway session state is not upstream deletion or immediate memory erasure. Runtime roots should be read-only and writable storage memory-only where supported; deployed enforcement remains a verification question.

## Telemetry: permitted signals and forbidden data

**Request telemetry is metrics only.** The narrowly authorized [startup diagnostics exception](#startup-diagnostics-exception) permits startup-only logs and lifecycle counts. No production request logs or request-level traces. Apply the same collection policy to real traffic in testing. Do not use access logs, trace-to-metrics processing, log bridges, automatic HTTP/GenAI instrumentation, profiling or session replay as a back door to collecting request data. Aggregate directly from closed, typed observations in application memory. Never put raw requests or raw errors into the telemetry pipeline to redact later.

Permitted after privacy gating:

- Coarse request/terminal-outcome counts and status classes.
- Fixed-bucket latency distributions, separated by success/failure.
- Coarse concurrency, admission pressure, resource use and process health.
- Bounded model, endpoint-class and infrastructure-slot dimensions.
- The subsequent [error/token extension](#typed-interface-failures-and-token-aggregate-extension) permits complete five-minute typed interface-failure counts and input/output/cached-input token sums. They were **not part of the first pass** and remain unimplemented/unqualified by this policy change. Cost totals remain deferred and prohibited.

**Never collect into telemetry or export:**

- Prompts, responses, history, documents, tool payloads, content hashes or derived text/features.
- Request bodies, raw URLs/paths/query strings, headers, cookies, user agents, client/server IPs, DNS/network flow records or identifying hostnames.
- Credentials, account/payment identifiers, session/conversation/request/trace/span/submission/reservation IDs, onion identifiers, or stable user pseudonyms. Hashing an identifier does not make it acceptable.
- Exact request timestamps, per-request token/cost events, request/response byte sizes, or exact individual duration samples.
- Raw SDK/upstream/parser errors, panic payloads, stack traces, environment variables, process command lines or memory/core dumps.

The no-stable-pseudonym rule concerns people/accounts/sessions. An operator-assigned **infrastructure slot** such as `gateway-01` is allowed solely to diagnose gateway resources. It must not identify a customer, encode a hostname/IP, or describe a dedicated user deployment. Source request values cannot set telemetry labels. Error categories must be a reviewed closed enum, not exception strings; detailed content-free error codes remain transient user diagnostics, not automatically exported labels. The extension below permits only an explicitly reviewed aggregate projection, never arbitrary diagnostic codes.

## Aggregation is necessary, not sufficient

1. Sanitize and aggregate **before data leaves the gateway trust boundary**. The direct exporter enforces the final closed metric/resource/datapoint allowlist locally; there is no Collector sidecar. Drop unknown metric names, attributes, resources, exemplars and free-form scope metadata; fail closed on sanitizer errors.
2. Export fixed, non-overlapping time windows, not cumulative request counters whose successive values expose new events. Export only bucket boundary timestamps, never request times, start times or last-seen times. Do not flush partial request windows on shutdown.
3. Review the **complete family of released values**. Model × instance × endpoint × outcome can isolate one request even when each individual label is low cardinality. Sparse counts and histogram bins can reveal coarse information about individual activity; the MVP decision below accepts this residual risk rather than promising anonymity.
4. **2026-10-09 operator decision:** use complete five-minute aggregates without a minimum-observation threshold or linked sparse-cell/complement suppression. The operator explicitly approved release of sparse aggregate counts and bins. Preserve complete-window and lifecycle/arithmetic consistency checks; this is not permission for per-request events, content or identifiers. Never claim k-anonymity, differential privacy or resistance to correlation, and do not introduce user-identifier collection to claim such a guarantee.
5. Missing or withheld invalid/incomplete values mean **unavailable**, not zero or healthy. Dashboards and alerts must preserve this distinction. Do not add fine-grained loss or suppression counters.
6. Real-traffic export uses only the reviewed MVP release scope below. New dimensions, finer cadence, resource scopes or additional data require another concrete release review; a destination environment or credential does not grant permission to expand collection.

### Reviewed MVP release scope

The configured production runtime may release complete, non-overlapping five-minute request windows under the [2026-10-09 MVP decision](docs/telemetry-mvp-five-minute.md). Active atomic cells and populated distributions may contain a single observation. There is no ten-observation or linked-sparsity gate. All simultaneous model/endpoint/outcome/delivery/occupancy tables still share complete-window closure and structural validation: 300 actual occupancy polls, matched lifecycle/distribution counts, bounded valid enums and checked arithmetic. Invalid/lost observations discard the affected window; startup and restart discard partial windows. Do not export independent overlapping marginals, per-request records or fine-grained loss counters. Production and synthetic qualification use this same contract. Historical ten-observation vectors remain historical evidence, not the current release requirement.

Gateway-process CPU cores used and approximate RSS bytes may be exported as complete one-minute means of six valid readings. No raw reading, PID, process metadata, inferred capacity or percentage is exported. These measurements cover the gateway process, not the enclave, cgroup, helper processes or model GPU.

The operator approved six configured admission capacities on 2026-10-08, including the historical New chat lane. The API-only cutover removes that lane; the target has five **configured application admission capacities**, independently of request-family release: connection 64; generation, heavy and ingress 4 each; control 1. Derive these from the same constants that construct the server's admission semaphores, never from currently available permits. Export only the existing `possums.admission.capacity` gauge in `{permit}`, with `source=configuration`, `scope=gateway` and the five closed lane labels, after all six ten-second samples complete a fixed minute. Missing/late samples remain unavailable; timely CPU/RSS source failures need not suppress independently valid configuration samples. These are shared application limits, not current occupancy, per-model capacity, CPU allocation, memory headroom, cgroup or enclave limits. This cutover neither relaxes request-family release validation nor enables additional resource scopes; five-lane local source/wire checks are recorded in [API-only verification](docs/verification.md#api-only-cutover--local-source-verification-2026-10-09), while deployment verification remains pending. Deployment status and tests belong in the release evidence, not this authorization statement.

The subsequently operator-approved control-admission removal candidate deletes the single shared control-request semaphore. Its configured-capacity export omits `control` rather than fabricating an unlimited or zero capacity; connection, generation, heavy and ingress capacities remain unchanged. It adds no metric names, labels, finer cadence or request-level signals and preserves complete-window and lifecycle/arithmetic validation. Control request parsing remains bounded, but the historical single-control-lane memory arithmetic no longer applies. This is source policy authorization, not evidence of deployment or whole-process memory headroom. See [control-admission verification](docs/verification.md#control-request-admission-removal-candidate).

The 2026-10-09 quota-simplification candidate removes the independent generation semaphore, not the existing heavy-memory admission bound. The generation capacity value remains the effective bound inherited from the configured heavy lanes, rather than a separately enforced generation quota. Passive generation lifetime tracking preserves the existing occupancy observations; it cannot reject a request or change accounting. This changes no metric names, labels, cadence or configured capacity values. Candidate verification and deployment status are recorded separately; it does not claim unlimited gateway parallelism.

The subsequent operator-requested inference-limit removal candidate explicitly deletes the heavy/ingress request-admission ceilings without a replacement count, queue or byte-based admission mechanism. Non-rejecting lifetime observations may remain, but configured-capacity export must omit generation/heavy/ingress and retain only the existing connection capacity; no zero, unlimited or invented capacity is allowed. This narrows the configured-capacity release and adds no metric names, dimensions, cadence or request-level signals. Per-request transport/parser defenses, account credit, accounting and lifecycle rules remain; disconnected accepted work is not bounded by the connection limit. The former aggregate workload-memory arithmetic no longer applies, and no whole-process memory-headroom guarantee is made. The delivery-backpressure candidate may pause upstream polling while a connected reader stalls, retaining only bounded transport/event state plus the accepted request's owned input. Disconnect must wake blocked delivery and resume the same upstream operation through settlement without replay; connected stalls may delay final usage, settlement and graceful drain. This adds no content persistence or request-level telemetry. Implementation/runtime evidence must be recorded separately before claiming deployment.

This is **MVP data minimization, not anonymity**. The pipeline deliberately cannot count distinct users; sparse released aggregates can describe one person's activity. Five-minute bucketing and CPU/RSS averaging do not prevent external timing correlation, especially on a quiet gateway. Model names and the shared infrastructure slot are operational labels, never user/session keys; do not describe them as proof that a released population contains multiple people. Missing/incomplete request windows may still produce no chart. Keep Honeycomb access restricted and these limitations disclosed. The existing prohibition on content, identifiers and per-request events is unchanged. The subsequent extension below narrowly permits aggregate token sums, not per-request usage or cost export. Source/wire tests and live-versus-local scope are recorded in [verification](docs/verification.md).

## Typed interface failures and token aggregate extension

The operator requested this extension after intake adopted mandatory interface-failure classification. **Policy and planning authorization only:** no implementation, activation, ingestion, installation or deployment is established here. The implementation contract and staged acceptance are in [the overhaul plan](docs/interface-error-token-metrics-plan.md). This narrowly supersedes earlier blanket token-export exclusions; cost export and all other content/identifier/per-request restrictions remain intact.

### Mandatory typed interface failures

Every project-controlled external-facing interface, inbound or outbound, and its supporting startup/background/cleanup paths must classify observed failures from supported typed sources and actual protocol evidence. Include API/listener/middleware, attestation/helper, authenticated catalog/tokenizer/inference, stream/delivery and accounting boundaries. A future gateway↔intake adapter inherits this policy but is not authorized by it. Existing client diagnostics must preserve categories; this extension authorizes no client telemetry upload or Pi/T3 host changes.

Known errors retain a stable locally authored code, failing stage/constraint, actionable next step and independently evidence-supported operation/billing outcome. Unexpected exceptions require a stage-specific **cause unknown** type, not generic text, an invented root cause or exception-string classification. Raw causes, panic payloads and hostile values never enter diagnostics/metrics. Classification is mandatory even with telemetry disabled; process loss, external SDK-swallowed failures, startup/shutdown and incomplete/lost windows may prevent observation or delivery. Document these limits rather than promising every exception reaches Honeycomb.

Keep the smallest sufficient expected-error set. Remove redundant defensive rejection where an authoritative boundary already guarantees the invariant, not necessary trust/accounting/parser checks. Normal duplicates, voluntary cancellation and orderly shutdown are not fabricated faults. Preserve known settlement/refund and primary failures through subsequent encoding/delivery/cleanup failure. No diagnostic-triggered inference, retry or replay, no weakening verification/tool gates and no silent change to shipped clients' default wire contracts.

Permit complete five-minute failure counts from a reviewed closed `error_type` projection with stage-specific unknown fallbacks. Detailed diagnostic codes are not automatically labels. Pin reachable mappings/cardinality and a sole owner per failure before instrumentation. Propagating/wrapping one failure does not recount it; a genuinely independent later fault may count separately. No endpoint×model×status×error cross-product, raw errors, logs, traces, financial values or request identifiers. Telemetry machinery failures remain classified transiently and do not recursively instrument themselves. Withhold unqualified coverage; missing hooks/timer coverage must never produce healthy zeros.

### Observed usage token sums

Permit only complete five-minute sums of **input tokens (including cached input)**, **output tokens**, and **cached-input tokens (a subset of input)**, partitioned by the existing reviewed qualified model map. Sum those disjoint partitions in queries for across-model totals; do not export overlapping global marginals or dynamically add catalog model labels. Every supported model contributes through named labels or validated `other`. No endpoint/outcome/user/session dimensions, cache scope, costs, balances or per-request usage events.

Reuse already validated authenticated usage evidence: final usage on completion or the last trustworthy cumulative usage on interruption, once at the sole generation terminal attempt. Never sum snapshots, add reasoning twice, use tokenizer estimates/text length, or count duplicate submissions/receipts. Export only numeric aggregates, not raw evidence/header/parser objects. Accounting failure must not erase known usage or fabricate a confirmed charge/refund. These are **observed usage totals**, not exact provider invoices or all unobserved compute; missing usage is not measured zero. Cached totals remain unavailable for the whole window if any usage-bearing generation lacks trustworthy cache counts; valid input/output may still release. Known zero cache is permitted only for a populated fully cache-qualified partition.

The operator-requested release accepts sparse complete five-minute error/token aggregates under the existing no-minimum-count decision. On a quiet gateway, token totals may disclose one request's approximate lengths/cache reuse; error categories disclose failure activity. Combined model/resource/timing data can aid correlation; across-model totals are not anonymization. No anonymity, differential privacy, distinct-user or invoice-parity guarantee is made.

Preserve complete-window closure, checked arithmetic/exact serialization, bounded state, final local allowlist, boundary-only timestamps, no exemplars, one owned sender, no spool/replay/shutdown partial flush and `OTEL_SDK_DISABLED=true`. Each new family needs qualified observation coverage and explicit unavailable semantics before activation. Unknown enums, lost observations, arithmetic/clock/completeness faults fail closed for the affected family; telemetry cannot block service or change accounting. Existing request-family integrity remains unchanged. Use supported SDK/exporter types and existing helpers, not a second provider parser or generic diagnostic framework.

Required evidence includes the boundary/type/owner inventory, negative known/unknown and hostile-data tests, once-only cleanup/terminal races, exact multi-model and cache-availability vectors, actual supported OTLP wire inspection, off/outage independence, shipped-client decoder compatibility and generated-image/runtime verification. Link this section and that evidence in every implementation change. Honeycomb US/provider-default MVP retention/access and platform unknowns are unchanged. This documentation change authorizes no new dashboard/alert, live probe, export activation or deployment.

## Startup diagnostics exception

The operator requested platform and Honeycomb startup logs plus aggregate startup metrics while investigating a failed rollout, and explicitly selected the **normal Honeycomb dataset**, not a separate startup dataset. Startup traces were also acceptable to the operator; this implementation selects only logs and metrics, without introducing a tracing framework. This exception changes startup observability only, not request collection, inference, recovery or deployment authorization.

- Emit finite, locally authored startup milestones and a terminal outcome to process stderr (subject to platform capture) and, with valid existing allowlisted telemetry configuration, direct authenticated Honeycomb US OTLP. Reuse the normal service resource/destination and credentials; no additional dataset, arbitrary destination or identifying resource discovery. Retain provider-default MVP retention/access boundaries; effective log retention, platform capture/access/retention and log-ingestion key capability remain unverified until separately observed. No secondary archive. Startup timing reveals process lifecycle and can aid correlation; it is not anonymous request aggregation.
- Preserve useful typed causes, failing stage/constraint and actionable messages. Raw startup errors were offered by the operator, but arbitrary exception text is **not collected**: it can contain credentials, private configuration, URLs or identifiers. No raw SDK/parser/io errors, panic payloads, stacks, config values, host/path/onion identities, request data, dynamic attributes or trace/span identifiers enter these records. A supported observed HTTP status may be included, never an inferred status or root cause.
- In this inactive HTTPS-only backup, a startup-only owner records configuration, account parsing, signal setup, verified upstream connection and TCP binding: five stages plus one terminal record, at most six records. It terminates at local initialization completion, failure or interruption, before request acceptance. It must not observe request/peer callbacks or log later runtime activity. Initialization completion is **not** verified serving, successful inference, cancellation or settlement evidence.
- Permit one bounded startup lifecycle count family, partitioned only by closed stage/outcome, at the terminal startup boundary. This is a startup-only snapshot exception, **not** a partial five-minute request window. Count observed lifecycle transitions once; no healthy zeroes, per-request observations, durations, models, detailed error-code cross-products or overlapping totals. Existing request-window integrity and shutdown-discard rules are unchanged.
- Deliver logs and startup metrics best-effort once under a finite shared deadline, with owned cancellable transport and no retry, spool, detached upload, global logger/log bridge or automatic HTTP/GenAI instrumentation. Preserve the original startup failure/exit code if delivery fails. A closed local delivery warning must not recursively export itself. `OTEL_SDK_DISABLED=true` disables both Honeycomb signals, not separately captured platform stderr. Diagnostics must initiate no inference or replay and must not weaken trust/accounting/drain ownership.
- Pre-main/runtime-construction faults, panic/abort/OOM/SIGKILL, blocked/lost platform stderr, unavailable credentials/network and process termination can prevent delivery. Do not promise every failure reaches Honeycomb. Successful HTTP submission does not prove query visibility, retention or serving. Platform boot/container/shim failures before this executable runs remain outside its reporting boundary.

The Tor-specific post-launch readiness exception is removed in this backup, along with its observer, FIFO presentation and delivery hooks. Historical PR90 evidence remains in [the readiness record](docs/tor-startup-readiness-diagnostics-verification.md), not current collection authority. General startup implementation and historical offline evidence are tracked in [startup diagnostics verification](docs/startup-diagnostics-verification.md); current removal checks are in [backup verification](docs/without-tor-backup-verification.md). The failed v0.0.48 update remains unreconciled; this authorization permits no automatic update/retry/cancel/rollback, live probe or export activation.

## Processors, retention, access and shutdown

- **Honeycomb** is a third-party observability processor, not inside the attested boundary. Send only approved aggregates and the closed startup-only logs authorized above over authenticated TLS directly to the US endpoint (no Collector sidecar). Honeycomb receives gateway network metadata as part of transport; it must not receive client addresses or request identifiers. Verify vendor-side transport/audit retention separately from metric retention.
- **MVP retention exception:** the operator accepts Honeycomb's provider-default metric retention; a custom seven-day setting is no longer required before first export. Public documentation describes 60 days for most customers, but that is not proof of this account's effective period. Record actual retention/deletion/backup information when available, and label unknowns accurately. Shorter retention (target: seven days) remains a post-MVP follow-up; do not silently extend retention beyond the accepted provider default.
- **Tinfoil** provides the enclave/inference platform and already offers container resource metrics and billing/usage APIs. Its platform collection, access, retention and backup behavior are a separate boundary, not controlled by a seven-day Honeycomb setting. Verify/disclose these properties; do not claim that locally disabling export turns off platform observability. Do not import API-key billing breakdowns or provider resource identifiers into telemetry.
- Limit Honeycomb access to named operators who need it; no public boards or unrestricted share links. Use environment-scoped ingestion-only keys where supported. Keep vendor/admin keys in runtime secret delivery, never a document or image. Do not place a Tinfoil admin key in the prompt-processing gateway.
- Enable the reviewed MVP aggregate families by default only with valid allowlisted Honeycomb US configuration and ingestion credentials; keep unapproved families closed. After local invalidation, the configured sender may resume only through fresh warmup/full windows with attempted-window watermarks preserved; never replay an old batch or infer healthy zeros. Keep a tested deployment-level disable setting (`OTEL_SDK_DISABLED=true`, applied at process start) and discard pending batches on process shutdown; no hot-toggle acknowledgement deadline or disk spool. Vendor outages, quota failures, sanitizer failures and disabled telemetry must not block inference or change reservations, settlement, refunds, retries or user responses. Do not automatically replay inference.
- On suspected leakage: stop export, revoke affected credentials if relevant, restrict access, arrange vendor deletion, and document a content-free incident record. Do not copy suspect payloads into tickets or chat as evidence. Deletion is incident response, not the primary sanitization control.

## Synthetic testing exception

Historical local qualification fixtures used the `test` label; the current Honeycomb destination is `prod` (initially expected to be `dev`). None of these labels grants the synthetic exception. To use this exception, use isolated, synthetic prompts and throwaway test accounts only, with no real user traffic or reused production credentials. The shared production gateway is not isolated merely because synthetic canaries are sent to it. This permits detailed **aggregate** breakdowns and controlled low-count fixtures to validate arithmetic, consistency and complete-window behavior; it does not permit bodies, identifiers, logs or traces. The exception must be deployment-controlled, not activated by a client header or request field. Do not mix synthetic and real traffic to manufacture enough samples for export. Retention, access control, secret handling and the export allowlist still apply.

## Required evidence for every telemetry change

- Identify the operational question, source, units, dimensions, window, retention, processor and privacy risk for each metric.
- Test hostile secrets/content in every boundary, including resource/datapoint attributes, errors, SDK defaults, exemplars, exporter diagnostics and export failures. Inspect actual outbound OTLP payloads with synthetic sentinels, not just configuration files.
- Test exact low-count aggregate encoding and disclosed sparse/correlation limitations, duplicate lifecycle observations, lifecycle/distribution consistency, restart/reset, disabled export and exporter outage. No metric may alter accounting or inference behavior.
- Inspect generated images/configurations and the deployed runtime. Record unknown platform properties as unknown, with phase/release labels.
- Record the policy reference and pass/fail evidence in [`docs/verification.md`](docs/verification.md). Do not publish “no telemetry,” “no logs whatsoever,” “operator cannot see plaintext,” or “retention is impossible.” Only make scoped claims supported by the tested configuration.

## Inspiration, not equivalence

Sources checked 2026-10-07:

- [Mullvad's no-logging policy](https://mullvad.net/en/help/no-logging-data-policy): the closest operational model—aggregate connection/system health and transient account concurrency. We do **not** adopt its short-lived website access logs, and we disclose Honeycomb rather than claiming no external analytics processor.
- [Signal's privacy policy](https://signal.org/legal/): minimize retained information and avoid monetizing it. Its inability to decrypt message content does **not** apply to inference plaintext in our enclaves.
- [Proton privacy policy](https://proton.me/legal/privacy) and [Mail-specific policy](https://proton.me/mail/privacy-policy): explicit processor, metadata and retention disclosures. Proton documents IP-logging exceptions and mail metadata; neither is permission to introduce those practices here. We do not inherit Proton's jurisdiction, infrastructure ownership or encryption claims.
- [Honeycomb data protection](https://docs.honeycomb.io/security-compliance/security-data-protection/), [Tinfoil container metrics API](https://docs.tinfoil.sh/admin/admin-api): provider documentation is a starting point, not deployed evidence. See the [telemetry plan's source list](docs/telemetry-plan.md#sources) for implementation references.
