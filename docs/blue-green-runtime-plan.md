## Complete target cutover and user experience

**Target, not a qualified platform guarantee:** old blue serves users while new green boots held → green passes health and exact public verification → promote new traffic to green → independently verify production and align paid latest → blue finishes existing connections and accepted accounting owners → retire blue only after both are drained. Do not close blue admission before the traffic switch merely to create a maintenance window. Requests racing cutover can still reach blue after its fence closes; test and report that boundary. The platform must provide the necessary supported retention/control; none is invented by this document.

Users normally see no interruption while green boots or while existing blue requests finish. A failed candidate remains held and must not replace blue. After a successful switch, the initial Pi request or a native tool-continuation request in the same authorized user run can recover eligible stale auth/key **setup** failures as specified below, adding verification/login delay only to that failure path. They share at most three deployment-recovery attempts per run, with bounded cancellable backoff and no generation replay. This preserves the transcript, not old gateway sessions or ledger state. Healthy turns add no public attestation/evidence/login requests.

Possible visible interruptions remain:

- New setup during the production/latest propagation gap: full verification fails closed before inference; the user gets a content-free diagnostic and must submit deliberately later. No release-discovery fallback or automatic waiting loop.
- Recovery evidence fetch/verification/login fails or the report is unchanged: show the original/appropriate closed diagnostic; no prompt submission by recovery. Rate limits are a real availability dependency.
- Cutover occurs after setup, when inference might already have been dispatched: report the failure/unknown outcome; this recovery does not replay it. A physical disconnect can lose delivery while the retained old owner still finishes accounting.
- Exhausting the run's three recovery attempts, an unchanged report, or a terminal recovery failure ends the run with a diagnostic. Native tool continuations may recover before their next inference dispatch, but native retries, queued follow-ups, compaction and extension-originated work cannot borrow or replenish this permission. Keeping active connections alive still does not preserve every future request; no unconditional seamless-run guarantee.
- Platform crash/forced kill or accounting integrity failure: no claim of successful drain, preserved balance or confirmed refund. Candidate health cannot prevent all subsequent failures.

For lost client delivery, blue continues consuming the authenticated upstream to terminal: valid final usage settles once; upstream error/missing or invalid final usage refunds the reservation once when that accounting operation succeeds. The user knows an outcome only from an authenticated receipt/reconciliation, not from our intent to retain blue. Overlapping demo credit remains an unresolved release gate, not silently accepted by this sequence.

## Source facts driving the original design

These are the pre-implementation observations. The feature branch's local server implementation and corrected tests are now independently accepted; see [current scoped evidence](blue-green-verification.md). They do not describe a deployed code change.

- `src/main.rs::run`: `tokio::select!` abandons serving on SIGTERM, shuts down telemetry, then returns. Detached Tokio workers can therefore be destroyed during runtime exit.
- `src/server.rs::serve_with_header_deadline`: connection workers are detached. `request_admission` covers heavy/control resource admission but has no quiescence fence. A route can be awaiting public evidence/catalog when shutdown begins.
- `src/generation.rs::submit_core`: verifies evidence/catalog, then `Auth::admit_submission` reserves synchronously; immediately constructs `ReservedGeneration`. Charged preflight is detached; the SAME owner transfers synchronously to API composition even if its observer disappears.
- `src/generation_owner.rs`: `Terminal` makes one accounting attempt; armed drop refunds. `spawn_settling_worker` moves the terminal into `Settlement` and resources/lifetime marker into `Worker`. Explicit drop order destroys captured work before returning memory credit. A receipt or generation-observation count is not proof all captured work was cleaned up. `supervise` carries only closed results.
- Hyper-owned upstream upload data can outlive the accounting worker (`src/inference/upload_tests.rs::early_413_keeps_both_production_uploads_charged_after_worker_returns`). Lifecycle drain below covers tracked handler/preflight/worker envelopes, **not all transport-owned prompt buffers or heavy-lease references**. Preserve that regression; a stronger upload-cleanup guarantee requires a separately agreed hook with the timeout owner. Do not attach lifecycle ownership to shared heavy leases, which downstream delivery also retains.
- Delivery may outlive accounting; an HTTP disconnect never cancels accepted inference. Auth/submission/accounting state is memory-only. Fresh candidate initialization grants the configured demo budget again.

## Packet A — local lifecycle fence and drain proof

Expected files: new small `src/lifecycle.rs`, `src/lib.rs`, narrow integration in `src/server.rs`, `src/api.rs::chat`, `src/generation.rs`, `src/generation_owner.rs`, `src/main.rs`; focused tests next to lifecycle/owner/server tests. Exact edits depend on the timeout owner's interface rendezvous. No general orchestration/task framework.

1. Introduce one process-local lifecycle object with a synchronous admission fence, outstanding-operation count, completion notification and sticky integrity-failure state. States: serving → quiescing → drained (or drain-failed). Quiescing is monotonic/idempotent. No IDs or retained per-request records. Closing admission and registering root work use the same synchronization boundary, so zero cannot race an unregistered admitted operation. Success requires quiescing, zero outstanding work and no sticky failure. Both success and failure return **only after quiescing and zero outstanding work**, never early because a failure was latched. Subscribe/enable notification before the final locked predicate check; use a lost-wakeup-safe multi-waiter loop. No lifecycle mutex spans an await, accounting call or captured-work destruction.
2. Acquire a linear lifecycle ticket at request admission, **before handler awaits** (including evidence/catalog/body parsing). If quiescing, reject new API work through a fixed content-free not-submitted diagnostic; reject without upstream prompt transmission, auth mutation or new reservation. Diagnostic shape/category is coordinated with the diagnostics owner; no raw cause export or new auto-retry promise. The operation ticket covers requests that already crossed the fence, including control operations that can otherwise mutate state after drain appeared complete.
3. Keep the ticket through the handler. `src/api.rs::chat` obtains it from request extensions and passes it through both text and structured submission variants; state-scoped `AppState::generation()` alone cannot supply a request ticket. Synchronously share its lifetime into the *original* new-reservation owner before any await/spawn, with no fresh root registration after quiescence. No new reservation is created. Duplicates do not get a second accounting owner. A request admitted before the fence may complete its reserve after quiescing; it remains counted, so shutdown cannot report drained in that interval. Do not revoke an accepted token/account operation halfway through it.
4. Retain shared lifetime guards independently in the admitted handler, the **entire `ChargedPreflight` envelope**, and the original owner/`Worker`. Each envelope releases its guard after its captured work and local resource references are destroyed. Preflight can outlive owner failure or successful handoff (the existing `after_compose` hook exposes this); transferring only the owner's guard is insufficient. Preflight failure, pre-poll drop and unwind still destroy captures/refund once before envelope retirement. On successful handoff, transfer the SAME accounting owner with no cancellation or zero-count gap; shared lifecycle guards do not create a second accounting owner. `spawn_settling_worker` retains lifecycle lifetime when destructuring `ReservedGeneration`; dropping `Settlement` must not prematurely signal worker cleanup. Preserve existing capture/terminal/resource order and retire the new lifecycle guard last in each tracked envelope. Do not tie owner liveness to delivery queues, shared heavy leases or an HTTP body's lifetime.
5. Record terminal-accounting invariant failure inside `Terminal::finish`, including its `Drop` refund path, into the closed sticky failure state before retiring the owner ticket. Use the actual accounting result, not `GenerationTerminal::Settlement` (which can classify successfully refunded invalid usage). Do not depend on `supervise`, which can disappear or run after ticket retirement. Zero outstanding work after a settlement error is **not a successful drain**; failure still waits for every other owner/envelope to clean up. Upstream error/missing usage with a successful exactly-once refund is a completed owner, not an integrity failure. Do not retry accounting or expose error payloads. Runtime crash/forced termination is outside the graceful-drain guarantee.
6. Unit tests first: monotonic fence, admission/close race, simultaneous waiters/no lost wakeup, no late uncounted root registration, duplicate rejection, text/structured ticket plumbing and sticky failure. Lose the handler, pause after composition, let the worker settle/finish, and prove drain remains pending until preflight cleanup; also cover preflight failure/pre-poll destruction. Inject explicit settlement and drop-refund accounting failure while another owner stays held: wait remains pending until all clean up, then returns failure with no retry. Avoid polling sleeps; use existing deterministic pause hooks/barriers. Tracking is control-only and must work with telemetry disabled or exporter failure.

**Acceptance:** after quiescence, `wait_drained` cannot return success or failure while any tracked admitted handler, preflight envelope or original-owner worker remains. Success requires successful terminal accounting and cleanup of those tracked envelopes; failure waits for the same cleanup and returns only a closed result, not a fabricated settled/refunded user outcome. Neither result proves all Hyper-owned uploads/transport buffers or heavy references have disappeared. This is not full response delivery or session preservation.

## Packet B — voluntary shutdown orchestration

1. Register shutdown signals **before serving can admit work**; registration failure returns a closed startup failure rather than silently starting without SIGTERM handling. Retain the server future/task instead of cancelling it in the SIGTERM `select!` branch. On the first shutdown signal or fatal listener failure, sequence: close the lifecycle admission fence → stop accepts → publish sticky shutdown to existing/racing connections → request supported Hyper graceful shutdown → continue polling/joining retained server/connection work alongside owner drain. A connection racing registration must observe shutdown, not miss a one-shot broadcast. Preserve a fatal listener failure as a failure exit even when drain succeeds. Destruction of a connection-task container must not implicitly abort outstanding accepted work. Continue polling existing connection/handler work and detached upstream owners. Integrate through the timeout owner's agreed server hook; do not change their connection deadlines or upstream timeout semantics.
2. Separate two completion conditions: (a) admitted operations/accounting owners cleaned up; (b) retained connection tasks have finished or their already-approved transport policy has closed them. Never use (b) as a substitute for (a). Slow downstream delivery must not cancel upstream ownership. Do not wait for heavy permits alone: delivered chunks can retain those after settlement, and returning them does not establish a linear admission fence.
3. Keep the Tokio runtime alive until owner drain finishes. No new application grace timer that aborts inference and calls it drained. Do not let a second signal silently bypass owner drain; forced process/platform kill is recorded as unqualified termination, not guaranteed refund. Whether external termination provides enough time remains a platform gate.
4. After accounting/connection shutdown completes, dispose telemetry using its existing drop-pending/no-partial-window behavior. Never flush a partial window or add drain-stage traces. On integrity failure return a content-free failure exit status after cleanup; do not claim balance restoration or replay uncertain work.
5. Preserve a compatibility wrapper for existing serving test callers if needed; keep the new controlled entry point minimal. Deterministic tests cover shutdown before first accept, simultaneous accept/shutdown, post-fence keep-alive requests, listener failure with an active owner, repeated signals and connections finishing before their detached owner. Simulate SIGTERM intent without sending signals to production.

**Acceptance:** a local synthetic shutdown with held active, queued/preflight and downstream-detached work does not exit early; valid authenticated fake-adapter completion settles once, invalid/missing final usage/upstream failure refunds once, panic/pre-poll cleanup preserves owner/resource order, and accounting failure cannot produce successful drain. No complete-session claim. Existing HTTP/SDK defensive deadlines remain independent.

## Packet D — startup health gate

Readiness means startup configuration/initial verified upstream-client initialization completed and the HTTP service responds; it is not per-model inference availability, release verification, ledger continuity or successful drain. Keep probes out of application request aggregates, do not add logs/traces, and ensure real user control-lane occupancy alone does not mark the process unhealthy.

The current image has no curl dependency; do not assume a checker exists, enable a command against the old image or add restart policy changes. Without a config healthcheck, process startup counts as ready. A healthcheck gates startup readiness, not future availability or attestation identity. ## Packet E — bounded Pi deployment recovery before inference

**Selected planning policy:** failure-triggered recovery, not an attestation poll before every request. The initial request and its native tool continuations share **at most three deployment-recovery attempts per active explicit user run**, with short bounded cancellable backoff. Public trust may change between model requests only after full verification; it never changes during an already-dispatched generation. This is an explicit planning change to the previous run-pinned deployment policy. Existing expiry-renewal eligibility and native transient-retry policy remain unchanged. Expected scope: narrow changes in `clients/pi/bootstrap.ts`, `provider.ts`, the reference client's prepare/dispatch boundary in `examples/phase01/client.ts`, and focused native-Pi/offline fixtures. Use existing verifier, acquisition bounds, auth epochs/cancellation and closed diagnostics; no new crypto/wire decoder, background refresher or native retry expansion.

1. Associate a memory-only attestation-response SHA-256 with the immutable public evidence snapshot used for each successfully verified context. Hash the bounded exact response bytes consistently; this is only a change detector, not attestation approval, freshness or newestness evidence. Full-response serialization/compression changes can create harmless extra verification. Neither an unchanged hash nor a check failure extends trust expiry. Never persist/export the baseline or public hardware identifiers as diagnostics.
2. A fresh idle explicit interactive/RPC turn establishes a cancellable run-scoped recovery budget. Its initial model request and subsequent native tool-continuation requests use cached trust/auth and setup normally, sharing that budget. A tool continuation prepares the next model request with already-completed tool results; it does not execute those tools again. Healthy requests add only local bookkeeping—no attestation, GitHub/AMD or extra login request. Model catalog/submission-token operations retain their current behavior; latency/performance is a design expectation, not benchmark evidence.
3. Only a validated closed unauthorized setup result **and affirmative local proof that inference dispatch has not begun**, plus qualified native request permission, may trigger initial recovery activation. Generic endpoint-binding/decryption errors are NOT a supported stale-key discriminator and remain terminal; key-recovery entry requires a separately supported discriminator. The current flow fetches the authenticated catalog, then `/v1/submissions`, then `/v1/chat/completions`. A token-issuance operation can have uncertain control-state effects without having sent inference; do not confuse those with reservation/generation outcomes. Add an explicit local dispatch boundary before the earliest operation that could send inference. Do not infer safety from HTTP status, raw error text, absence of output, `issued`, or successful later verification. Exclude generic parser/integrity/settlement failures, arbitrary transport failures, bad credentials with unchanged evidence, insufficient credit, duplicate submissions, abort and any inference-dispatched/uncertain path. The full verifier still fails closed on any trust-policy violation.
4. Under the same originating explicit run's current cancellation/account/session guards, consume the shared recovery budget before any await and make one bounded credential-free acquisition from the fixed paid production attestation endpoint. An unchanged report or failed acquisition also consumes an attempt. Use a bounded iterative loop, not recursion; each subsequent attempt must still have affirmative local pre-dispatch proof and current run/cancellation/account guards. Unchanged report and definitive trust-policy violations stop recovery immediately. Only narrowly observed public-acquisition/control transport interruption without cancellation, deadline/idle expiry, or HTTP 408/502/503/504 may use a remaining attempt; unknown classification fails closed. Astra's reviewed delays by attempt are 0, 250 and 1,000 ms, cancellable. Each attempt is bounded by existing `LIMITS.bootstrapMs` including setup. Unchanged hint, abort/replacement, fresh-auth 401/403, rate limiting, redirects/binding violations, malformed/oversized evidence, certificate/signature/provenance/measurement/key-policy failures, catalog validation, credit/duplicate errors and dispatched/uncertain chat are terminal. Do not parse error messages or add an automatic latest-propagation wait. No automatic waiting beyond this budget or inference replay. If acquisition finally fails, show a closed acquisition diagnostic. If changed, invalidate the old trust/auth/catalog context and perform full release/provenance/hardware/key verification under the existing fixed authority, even though local trust expiry has not elapsed. Reuse supported verifier libraries; no native-v3 bypass, arbitrary release origin or unsigned release hint.
5. After successful fresh verification, authenticate and refresh/validate the selected model's live catalog. Publish renewed trust/auth/catalog/baseline in one current-epoch step. The new baseline must come from the **actual successfully verified snapshot**, not the earlier hint response (which may race another deployment). Clear the old reconciliation window as existing renewal does. No model substitution, output-cap reduction or credit claim. Failure leaves no usable stale context; Stop/account change/session replacement suppresses late publication and inference. Renewal between tool rounds must preserve the current authorized run and previously completed tool results/receipts; do not accidentally invalidate that run through generation/run-epoch changes, or authorize an obsolete one through auth-epoch changes.
6. Resume/retry setup within the **remaining three-attempt shared run budget** for the pending model request using its same prepared messages/tool results, then dispatch its inference once. Do not rerun input/payload hooks, replay tool side effects, mint a second original accounting owner, or use a global retry loop. An uncertain token issue is not a license to retry the chat endpoint. If resumed setup fails, another attempt is allowed only within the remaining shared budget and the same strict pre-dispatch/classification conditions; otherwise stop. If a switch happens between setup and inference, normal channel checks fail safely; a generation with uncertain dispatch is not resent by this recovery.
7. Permission belongs to the originating explicit user run and can be consumed by its initial request or a confirmed native tool continuation, at most three attempts total. A continuation receives no fresh budget. Native retries, compaction, queued steering/follow-ups and extension-originated/nested work cannot initiate this recovery, borrow permission or reset it. Ambiguous run provenance fails closed. Existing separately approved native transient-retry policy is unchanged; this new mechanism must not broaden it. Native retries may already represent new submissions with possible charges, not deployment-recovery replay authorization.

Tests alongside implementation: healthy path has zero new acquisition/login calls; changed hint triggers one full forced verification/login and at most one inference dispatch; unchanged hint and failed/hostile acquisition do not recover; wrong signer/tag/measurement/key remains fail-closed; Stop/account/session races publish nothing late; two rotations use the actually verified baseline; hooks run once; setup token-issuance uncertainty does not imply generation safety; inferred/explicit post-dispatch failures never enter deployment recovery; eligible native tool-continuation recovery preserves completed side effects/results and prior receipts, never reruns tools; initial/continuation requests consume one shared three-attempt run budget; a fourth attempt never occurs; backoff is bounded/cancellable and only approved transient failures repeat; definitive trust-policy failures and unchanged reports are terminal; no recovery during native retries/compaction/queued input or nested extension work; original diagnostic and billing evidence survive recovery failure; no secret/ID/content output or status-triggered inference. Requalify against the actual integrated Pi 1.0.4 pair without install/live inference.
