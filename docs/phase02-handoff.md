## Implemented

- **Gateway:** bounded OpenAI function declarations, choices, assistant calls and matching tool-result histories; optional `tool_protocol` catalog metadata from an independent profile, never a catalog claim alone. Unsupported profiles fail closed. Tool-inclusive tokenization and generation share one structured invocation. Existing maximum-cost reservation, context enforcement, heavy-resource admission and detached sole settlement owner remain shared with the text path.
- **Streaming:** structured upstream SSE/JSON decoding now uses the pinned Tinfoil SDK, with a small gateway tool/usage validator rather than a parallel provider decoder. Bounded call metadata and opaque argument fragments; no complete generated arguments or answers buffered by the gateway. Text remains compatible with the existing web path. Quoted upstream rate strings accompany settled receipts from the submitted snapshot.
- **Reference client:** bounded data-only schema/message admission, finite JSON numbers, duplicate-key/argument limits, optional abort, immutable validated stream hooks, logical payload-hook replacement revalidation, sanitized response hooks, and authenticated receipt gating. Existing text-call shapes remain supported. Tool argument objects are assembled and validated at the client before executable completion.
- **Pi:** native provider extension pinned to 0.99.2; verified public bootstrap before masked recovery input, memory-only bearer/recovery, authenticated live discovery, normal model picker, progressive native text/tool events and receipt-derived cost. Usual Pi tools are reused. Explicit text-only mode, replay authorization, logout/session epoch isolation, disabled warming and cancelled compaction are included.

A valid gateway `length` is deliberately a **terminal partial-answer error in Pi**, not recoverable `length`: Pi 0.99.2 omits the paid attempt before calling the compaction cancellation hook. The adapter preserves the answer, settled usage/cost and original authenticated finish in diagnostics, without an automatic continuation. Tools never execute on a partial/tool-error stream.

## Gates before live tool testing / release acceptance

1. **Qualify actual upstream profiles.** With a separately authorized, bounded funded canary, select exact IDs from the authenticated catalog. Verify tool-inclusive tokenizer/generation serialization, every supported choice, fragmented/multiple calls, complete matching results, UTF-8/argument limits, finish and authenticated final usage/EOF, and at least one complete tool-result continuation. Check accounting counters independently. A text-stream canary or fixture is not tool qualification. Stop on an uncertain generation; never replay it automatically. Keep any candidate qualification private until its evidence passes; do not advertise unqualified production capabilities.
2. **Land only supported profiles.** Record exact model IDs and protocol evidence for the production profile table. Preserve all supported models in the catalog, omit `tool_protocol` on unqualified ones, and reject selected-model tool requests rather than substituting a model or reducing its output allowance. Gateway model/profile changes require a new measured release.
3. **Release and approve explicitly.** Build and run the existing release provenance, privacy, attestation, key-binding, web and accounting gates against the new artifact. Acquire independently reviewed public evidence, then explicitly approve its measured identity/configuration. The existing v0.0.9 pin must not be renewed or changed as a workaround. Build the Pi artifact from the exact accepted source/dependency snapshot.
4. **Test the real user path.** Verify/login through the shipped extension, choose a qualified model, execute ordinary Pi tools, confirm progressive output and one reservation/settlement per invocation, compare receipt charges with balances, and test duplicate submissions, insufficient credit before prompt transmission, catalog/trust failure, abort/disconnect, upstream failure and crash recovery. Re-run full transport/TLS/Chromium and package privacy/network checks. Check that receipt-less interruption is presented as unknown billing and never automatically replayed. Exercise hostile terminal/Markdown output and remote-resource handling; the local fixtures do not establish whole-Pi rendering or network safety.
5. **Record acceptance, not intent.** Update the verification record only with observed behavior and assumptions. Keep endpoint metadata/live catalog changes, store/payment association, traffic correlation, runtime compromise, open egress, dependency behavior, local Pi retention/tool authority and platform unknowns explicit.

No claim of full Phase 0.2 completion, a usable production tool model, audit acceptance or release readiness follows merely from the passing local suites.
