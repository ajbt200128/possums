# Pi client failure policy — approved source candidate

This operator-approved policy supersedes the earlier Pi gateway-transient generation-retry and terminal-error policies **for this client source candidate**. It changes neither gateway HTTP/accounting outcomes nor deployed/installed artifacts. No installation, deployment, credentials or live inference are authorized by this change.

## Turn and session behavior

- The operator subsequently selected warning-only stops for classified GitHub/AMD public-evidence availability failures: release discovery, manifest redirect/download, release provenance or AMD certificate acquisition, with observed transport/timeout/HTTP/rate-limit constraints. These are not authenticity rejections. They do not latch a fatal host turn, including native auth resolution outside a run hook; they still authorize no credentials/inference until complete fresh verification succeeds. Startup failure caching, expiry/recovery budgets and retry policy are unchanged. Schema/binding/appraisal failures and other unavailable gateway trust remain closed/fatal. See [restoration evidence](pi-v3-cache-restoration-verification.md).
- Apart from that acquisition-availability presentation exception, a fatal Pi turn and blocked subsequent dispatch are reserved for inability to confirm the correct backend: attestation/release provenance/publisher/endpoint-key verification, expiry without fresh verification, or authenticated response binding/integrity failure. Previously verified trust never overrides a current decryption/authentication failure. No content is dispatched while trust is unavailable. A new explicitly verified trust session is required after a latched integrity failure.
- Operator-approved key-rotation recovery: an otherwise valid actual TLS peer whose SPKI differs from the verified key may nominate the existing bounded, credential-free full setup re-verification **only before the monotonic inference-dispatch latch**. This observation is not proof of deployment or approval of the peer. Parsing/hostname/date/public-evidence certificate failures, decryption/integrity failures and every post-dispatch failure remain fatal. Replacement requires the complete existing verifier/freshness checks, fresh authentication and selected-model catalog under current run/account/cancellation guards; no new budget, credential-before-verification path or inference replay. Failed trust replacement remains closed; the normal new-session workaround is unchanged.
- Other failures stop gracefully with a closed, affected-user warning: missing receipt/finish/DONE/EOF, interrupted delivery, upstream operational rejection, SDK/content/assembly problems, unavailable metadata, accounting/display and local hook/presentation failures. Keep the resident client/session, received text and actually received authenticated money. A failed turn is not a dead session.
- Pi `done/stop` in these cases is a **host control-flow stop**, not evidence of successful backend generation, cancellation, refund or settlement. `possums_turn_warning` explicitly records that backend completion and tool authorization were not established. Do not automatically retry/replay inference or continue because of a warning. Deliberate next user turns remain possible; each new submission may charge again.
- Remove provisional `toolCall` blocks from the terminal message on interruption, incomplete/refunded/length output, or local assembly failure. Never emit executable final calls from uncertain delivery. Complete calls still use Pi's supported parsing and native lookup/schema enforcement; a model's undeclared tool becomes a native tool error, not a duplicate provider-policy rejection. Existing Pi lifecycle/abort/account guards and separately authorized pre-dispatch setup recovery remain; warnings introduce no continuation/retry/renewal mechanism.
- Native compaction may decline an incomplete/warned summary without saving a checkpoint or invoking an alternative summarizer. This is not an inference replay or session reset. Existing native threshold compaction can also submit a fresh summary after a high-usage warning turn; it does not replay the original generation. Do not claim warnings prevent all autonomous host inference.

**Native pre-adapter cancellation limitation:** intentionally canceled/obsolete authentication must not return the reusable request marker or mutate replacement failure state. Pi 1.0.4/1.1.0's auth result supports credentials or “not configured,” not a warning-only canceled turn. Rejecting stale auth therefore yields the host-owned error `API key auth failed for provider possums: possums_login_cancelled` before the adapter runs. This is intentional lifecycle cancellation, not backend distrust: no dispatch, no trust latch, and the valid replacement account remains usable. The operator explicitly accepted this narrow intentional-cancellation presentation exception after the full offline checks; ordinary operational failures in a current authorized turn remain warning-only.

## Gateway-authoritative accounting and forward compatibility

Accept additional gateway response fields; normalize understood fields and discard unknown fields before provider hooks/diagnostics. Required protocol fields remain readable/typed, request dispatch authority remains closed, and cryptographic formats/publisher verification are unchanged. Unknown server errors/messages never become diagnostic text.

Use authenticated gateway maximum reservation and charged total. Catalog unit rates are upstream prices: Pi model input/output price metadata remains an **indicative retail estimate with the gateway's 30% markup**. It is not used to recompute or validate received charges. Do not recompute a reservation or require token-sum, cache-subset, reservation-balance, markup/evidence-category or full-price equality. Unreadable optional metadata cannot erase a readable authenticated charge. Missing outcome is **unavailable**, not inferred settlement/refund. An authenticated receipt arriving before interrupted terminal delivery remains received billing evidence, not authorization for successful response delivery or tools. A bare error's refund claim still requires authenticated EOF; interruption does not confirm it.

Pi's numerical usage is populated only from readable gateway counts, with unavailable values represented by required zero placeholders and disclosed as unavailable. Prompt input remains the gateway's reported inclusive prompt count; cache count and total are reported independently, not used to manufacture uncached counts or charges. Display total charged directly. Exact microunit strings are retained in the existing native receipt/charge diagnostic; ordinary received charges use Pi's native `usage.cost.total` accounting without an extra UI warning. Actionable turn and explicitly unknown-billing warnings remain; Pi's floating-point dollar total is approximate for large values. No safe-integer display failure changes the observed money to unknown.

The current gateway contract supplies **no authenticated input/cache/output charge components**. Those component zeros are unavailable placeholders, not free inference; no proportional split, clipping or rounding residue is fabricated. Future exact components need agreed gateway field names/units; this patch does not invent a component protocol. Reconciliation remains unavailable for unknown accounting outcomes and never proves upstream invoice agreement.

## Privacy and delivery boundaries

Follow [PRIVACY.md: data handling](../PRIVACY.md#data-handling-boundaries), [forbidden telemetry](../PRIVACY.md#telemetry-permitted-signals-and-forbidden-data), and [synthetic testing](../PRIVACY.md#synthetic-testing-exception). Warning code/stage/constraint/status and actionable text are locally authored. Never include raw exceptions, rejected values, prompts/history, credentials, URLs, headers, identifiers or stacks. No diagnostic logger, retained raw payload, telemetry or support bundle is added. Sharing is manual and limited to content-free codes/stages/constraints/status, not billing details or request data.

Use the existing native provider stream and `ctx.ui.notify` notification path. Notification failure does not log, initiate work, fail the turn or revoke trust. Native Pi/T3 may persist ordinary assistant messages and safe diagnostics under their own history settings; this is not a whole-process transience claim. Print/JSON consumers can read safe native diagnostics; installed T3 rendering/notification delivery remains a separate verification boundary.

## Client simplification boundaries

Pi supplies current tools and normalized history through `getCurrentTools` and supported `convertMessages`, including retired tools and incomplete-history conversion. Keep image/mixed-provider/custom-namespace/constrained-sampling disclosures and null-to-empty tool-only assistant normalization. Payload hooks receive immutable credential/submission-free JSON snapshots; replacements are re-snapshotted and cannot change model/transport/submission authority.

The shared reference-client inference path also removes semantic transcript/tool admissions, duplicate argument accumulation/parsing and custom inference byte/depth/node/tool-state/chunk/frame/SSE quotas. This affects reference callers as well as Pi: reference callers own execution policy and must not interpret a returned native finish alone as tool or billing authorization. The reference API can return a classified failure carrier with received accounting evidence; the Pi adapter translates non-trust failures into warning-only host stops.

Public-evidence/catalog/control acquisition and validation bounds, key/report formats, minimum authentication-tag length, SDK-native decoder limits, abort and read-idle semantics remain. Gateway parser/context/accounting limits remain outside this patch. Removing client quotas is not a whole-process memory-headroom guarantee.

Scoped offline verification and remaining external limits are recorded in [client simplification verification](pi-client-simplification-verification.md).
