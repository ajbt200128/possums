# Pi client plan — Phase 0.2

**Implemented status:** the historical plan below is retained, but its implementation/profile gates are superseded by the operator-approved scope in [release record](phase02-pi-release.md). The current provider targets Pi 1.0.4, loads as a normal package, persists credentials through native auth and supports native manual/threshold compaction. All authenticated catalog models advertise an assumed common tool profile, not individual qualification. See [usage and privacy boundaries](../clients/pi/README.md); exact live accounting and whole-runtime privacy acceptance remain unverified.

**Status: planned, not implemented or verified.** This small integration follows the [verified streaming-only inference API](../OVERALL_PLAN.md#phases) in Phase 0.1 and precedes the [Obsidian client](obsidian-plugin.md) in Phase 0.3. It does not add a Pi runtime to the gateway image or change the Phase 0 no-JavaScript web interface. The deployed `v0.0.5` gateway still buffers responses; see the [Phase 0 transition contract](phase0.md#planned-streaming-only-replacement).

## Deliverable

Ship a pinned Pi provider extension, using Pi's supported OpenAI chat implementation where compatible. Add only the integration needed for live model discovery, approved Possums gateway verification, a protected request channel, and streaming model events. Do not add Possums-specific agent tools, a proxy, a separate CLI/SDK, or a complete-response buffer/fallback. Text chat and ordinary Pi tool-call/tool-result rounds are in scope **only for models whose tool protocol has been validated**; each model invocation has its own reservation and settlement/refund outcome. Unsupported capabilities must not be advertised or simulated by parsing text. Images and other modalities are deferred until their API and accounting semantics are verified.

Fetch model metadata from the authenticated live gateway catalog. Fail closed if verification, authentication, or validation fails; do not silently select a stale or substitute model. Keep all supported models discoverable, including those a user cannot currently afford. Catalog prices and displayed maximum reservations are indicative: the gateway snapshots the authoritative rate at submission, rejects a selected model before upstream prompt transmission if its maximum reservation exceeds the account's available credit, otherwise reserves the maximum possible charge and settles authenticated actual usage at that quote. For a $5 balance, a Kimi request with a maximum quote above $5 returns a clear insufficient-credit error; Pi must not substitute a cheaper model or reduce output. Prices and concurrent reservations may change after model discovery. Do not persist a stale catalog as a usable offline fallback or enable prompt-cache warming without explicit retention evidence.

## Trust and accounting boundaries

Before any credential, prompt, or tool result leaves Pi, independently verify the approved Possums release and bind the **actual** request channel to the attested gateway key. An OpenAI-compatible URL or standalone `/attestation` check does not establish that binding. Use pinned, reviewed Tinfoil-compatible verification and protected transport; ordinary authorization headers are not protected merely by encrypting HTTP bodies. Never fall back to unverified HTTP, redirects, or an unapproved release. The gateway separately verifies its own Tinfoil upstream.

The gateway streams output without collecting a complete answer. A client disconnect does **not** cancel generation: the gateway continues consuming upstream until the stream completes or errors, without a special post-disconnect drain window. It settles from valid authenticated final Tinfoil usage even if Pi received only part of the answer; on upstream error or missing/invalid final usage it refunds the reservation and absorbs upstream cost. Pi must mark interrupted turns as uncertain, never silently resubmit after generation may have started, and explain that a deliberate new request may incur a second charge. Preserve the gateway's duplicate-token and process-restart semantics; verify Pi's provider and agent-level retry behavior rather than assuming defaults are safe.

Pi session files, local tool output, installed extensions, and the device are outside gateway attestation and can retain plaintext. Review provider diagnostics and event hooks for content/credential leaks. Neither Pi nor the telemetry pipeline receives a privacy guarantee from gateway attestation alone.

## Delivery gates

1. **Protocol spike:** Pin Pi and transport versions; exercise the deployed API to verify streaming chunks, final authenticated usage, tool-call deltas/results, and interruption behavior. If Tinfoil does not supply valid final usage, do not infer cost from emitted text or claim partial-usage billing. Test protected authentication and actual endpoint-key binding before choosing the implementation path.
2. **Thin provider:** Expose verified live models in Pi; stream text/tool events with correct usage, errors, cancellation, and session handoff. Reuse Pi's built-in request conversion where its contract fits; do not hand-roll another provider wire protocol merely to emit events.
3. **Negative and runtime verification:** Prove that invalid/stale evidence, wrong keys, unapproved releases, redirects, catalog failures, and intermediary capture release no credential or content. Test upstream errors, missing usage, downstream disconnect, abort, duplicate tokens, default Pi retry paths, tool rounds, context limits, and model/cost display against the real pinned runtime. Verify insufficient-credit rejection before upstream prompt transmission, including a $5 balance versus a higher Kimi maximum quote, with no model substitution. Inspect the packaged extension for dependencies, persistence, and unexpected network destinations.

**Acceptance:** a real Pi session selects a live model, receives a verified streamed answer and a supported tool round, reports an interrupted request honestly without automatic replay, and fails closed before leaking credentials or content on any verification failure. Record remaining unknowns rather than claiming compatibility from configuration alone.
