## Minimal implementation contract

- One startup owner after the healthcheck branch, before application configuration parsing; finite stage milestones and one terminal outcome.
- Closed typed causes with locally authored constraint/action messages, no arbitrary error/config strings. Preserve supported inference/Tor cause distinctions and unknown fallbacks.
- Stages cover configuration, accounts, signals, optional Tor preparation, verified upstream connection, TCP bind and optional Tor initialization. End before connection acceptance; do not instrument peer/request/runtime callbacks.
- Local initialization completion is not verified serving/onion reachability/settlement. Signal interruption observed before initialization completes is not failure or successful initialization. The terminal snapshot is committed before best-effort export; a later signal during export does not retroactively undo completed local initialization or establish that any request was accepted. Shutdown is checked before the terminal handoff; finite delivery can delay subsequent shutdown polling by up to its shared budget.
- Emit bounded platform stderr records and terminal Honeycomb log delivery, then consume the owner. Keep existing request metrics runtime and shutdown semantics.
- One startup lifecycle count family, closed stage/outcome partitions, observed transitions once, no overlapping total/healthy zeros/durations/request dimensions. Startup snapshot is separate from complete five-minute request windows.
- Reuse fixed Honeycomb US direct TLS transport, generated official OTLP messages, explicit resource and scope, no default discovery/context capture/log bridge. No new dataset header.
- Logs then metrics, one attempt per signal, each capped by the existing one-second transport timeout within a two-second shared deadline (the original source used a one-second shared deadline; see the fairness correction below). No spool/retry/detached HTTP driver. Dispose owned work before returning and preserve primary startup exit/failure. Export failure gets at most a closed local warning, never recursive export.
- `OTEL_SDK_DISABLED=true` disables Honeycomb signals; stderr remains subject to platform capture. Missing/invalid telemetry config does not change service startup outcome.

## SDK source findings — not runtime verification

Pinned Rust OTel 0.29 sources expose supported generated OTLP log messages. `SdkLoggerProvider::build` eagerly evaluates `Resource::builder().build()` through `unwrap_or`, even when an explicit resource exists. Normal SDK log emission can capture current trace context. Avoid that provider/emission path; construct official generated OTLP messages from the sealed startup projection instead. Reuse supported transport/protobuf types, not a custom wire protocol.

## Independent startup-delivery fairness correction — source only

Policy references: [startup exception](../PRIVACY.md#startup-diagnostics-exception), [forbidden data](../PRIVACY.md#telemetry-permitted-signals-and-forbidden-data), [shutdown/processor boundaries](../PRIVACY.md#processors-retention-access-and-shutdown), [required evidence](../PRIVACY.md#required-evidence-for-every-telemetry-change). Local isolated worktree based on `c497998`; no remote runtime, production, Honeycomb, inference or sibling race-fix operations.

**Reproduced controlled gap:** the original sequential logs/metrics implementation shared one second, while the reusable transport independently allowed one second per attempt. A real local TLS fixture withheld the log response until the client closed it; metrics then had no remaining budget and never connected. The new regression failed on the original implementation with `logs exhausted the only metrics delivery opportunity`. This proves starvation in controlled source behavior, not the initiating cause of the failed production candidate or the meaning of absent Honeycomb columns.

**Smallest correction:** keep sequential delivery and the existing transport's one-second attempt limit; reserve two seconds for the shared startup delivery deadline. No retries, concurrent uploads, new network tasks, spool, persistence, destinations, headers, SDKs or OTLP schema changes. Preserve the first known delivery failure even if the other signal subsequently fails; original startup outcome/exit is unchanged. A transport attempt timeout is now locally classified as `signal_delivery_deadline`, separately from the outer `shared_delivery_deadline`. These warnings never export themselves.

Latency/resource impact: successful fast delivery is unchanged; worst-case diagnostic waiting before service acceptance or startup-failure exit increases from one to two seconds, plus scheduling/disposal overhead. At most two connection attempts, one active connection and one encoded signal at a time; the second can now actually run after the first times out. Existing nine-record and transport/response bounds remain. No inference, billing, trust, readiness predicate, ordinary request-metric cadence or runtime drain ownership changes. Standard DNS can outlive cancellation without credentials/payloads; this is not a hard whole-process two-second exit guarantee.

Failure-to-visibility inventory (unchanged except deadline classification):

- `OTEL_SDK_DISABLED=true` intentionally skips both network signals while platform stderr remains. Missing/invalid allowlisted configuration also disables export without changing startup outcome; no automatic attempt or delivery claim. The existing parser does not report a distinct invalid-config warning.
- Enabled configuration that cannot construct transport yields local `startup_delivery_unconfirmed`, stage `startup_logs`, constraint `transport_configuration`. Request construction has `request_encoding`; sealed generated protobuf encoding has no recoverable error result. Allocation failure/process loss is not converted into successful delivery.
- Connection/DNS/TLS/HTTP I/O faults yield stage-specific `transport_cause_unknown`. The shared transport intentionally discards raw errors and does not preserve a finer connect/TLS cause; do not infer one.
- Rejected status or bounded HTTP response/body failure yields `http_response_rejected`; malformed OTLP protobuf yields `otlp_response_invalid`; decoded rejection counts or warnings yield `otlp_partial_success_or_warning`. The current shared transport collapses non-success status and response-limit/body failures and does not retain the exact observed status for startup presentation. That diagnostic-detail gap remains; this patch does not invent a status, broaden the shared transport or echo hostile response text.
- Per-attempt timeout yields `signal_delivery_deadline`; spent outer budget yields `shared_delivery_deadline` without opening another connection. Owned I/O is dropped; the first known failure survives later signal/disposal handling. At most one closed stderr delivery warning reports unconfirmed delivery, not a changed startup result.
- Valid HTTP 200 plus accepted OTLP response means submission acknowledged, **not** verified query visibility, retention or serving. Empty dataset metadata or no warning in a truncated stderr view proves none of these. Network delivery cannot be guaranteed.

No shared stderr flags or SDK loggers are modified. The existing pre-acceptance nine-record startup owner is out of scope and unchanged.
