### Reservation proof obligation — conditional mathematics, not a passed provider gate

Let `I` be **all billable input tokens**, `O` **all billable output including reasoning**, `C` an authoritative *shared* context bound, `M` a distinct output bound if one exists, and `p,q` the snapshotted, upward-rounded prices in USD microunits per million tokens. With nonnegative prices and no additional fees, the 30%-marked-up user charge is:

`charge(I,O) = ceil(130 * (p*I + q*O) / (100 * 1_000_000))` microunits.

**Only if** the provider establishes `I>=0`, `O>=0`, `I+O<=C`, `O<=M<=C`, with reasoning already inside `O`, the feasible-region vertices are `(0,0)`, `(C,0)`, `(C-M,M)`, `(0,M)`. The maximum numerator is `max(p*C, p*(C-M)+q*M)`; positive rounding is monotone, so round that maximum upward once. For `M=C`, this reduces to `C*max(p,q)`. That is the missing condition behind the existing `max(all-input, all-output)` implementation—not an unconditional proof. If `M<C`, the mixed vertex must be considered. If context instead bounds input alone, the rectangle permits `(C,M)` and the bound is `p*C+q*M`. If hidden reasoning is outside `O` or context, another authoritative bound is required. Tokenizer counts must be related to **billable** input, not merely accepted because a monetary charge happens to fit.

All products, sum, markup multiplication and rounding addition must use checked `u128`; reject on overflow or a result above `u64::MAX`, never saturate/wrap. Existing `src/catalog.rs::marked_up_cost` has those checks and upward fixed-point rounding. Existing tests exercise rounding, context rejection and overflow, but cannot certify provider constraints.

### Encoding, completion and defensive bounds

`IncrementalRenderer` borrows already-bounded incoming messages and the accepted prompt, emits escaped plain text in an open form/pre, and incrementally serializes canonical role/content JSON without collecting the generated answer. Empty assistant content is valid. JSON escaping plus base64url-no-padding fields preserves Unicode, NUL, CR/LF, quotes and hostile tags independently of HTML/form normalization. Ordered `h000000`… fields contain fixed **4096-byte decoded blocks**, except the final partial block. There is one fixed partial-block accumulator; delta boundaries and visible writes never flush it. The final manifest is exactly `1.NNNNNN.LLLLLLLL` (version, block count, decoded bytes).

The strict additive decoder bounds raw input before parsing, accepts only csrf/token/model/prompt, numbered history blocks and one manifest, and rejects missing/duplicate fields, encoded name aliases, unknown fields, out-of-order/gapped chunks, noncanonical base64 (including unused bits/padding), wrong lengths/version, malformed percent/UTF-8 input and invalid JSON schemas/roles/order. Decoding does not authenticate the form; the original auth/admission gates remain required at migration.

The checked conservative form prediction derives from the existing **8,388,608-byte HTTP body ceiling**. It reserves **7,060 wire bytes** for fixed field names/separators, 43-byte CSRF/token values, a 256-byte bounded ASCII model field at worst-case percent expansion, the 17-byte manifest, and at least **1024 next-prompt UTF-8 bytes** even under worst-case LF→CRLF plus percent expansion (6144 wire bytes).
