## Minimum implementation per phase

- Build only what is needed to complete the current phase. Do not pull future-phase infrastructure or speculative hardening into the implementation.
- Check provider SDKs and existing libraries before writing an adapter. Reuse their supported clients, stream decoders, types and helpers instead of reimplementing provider protocols.
- Keep custom code for gateway-specific behavior such as authentication, reservations, settlement, receipts and bounded stream state—not duplicate SDK wire handling. Tool-name/choice and argument validation for execution belong to the caller; a gateway settlement receipt is not tool-execution authorization.
- Check nearby code for reusable functionality before adding another helper. Remove superseded code within the task; propose unrelated cleanup separately.
- Keep existing required security/accounting behavior intact. Defer additional caps, abstractions and optimizations until the phase or production plan actually needs them.

## PR rollout labels

- The user or agent may explicitly apply `no-rollout-needed` after reviewing the complete PR diff and deciding that gateway rollout is unnecessary (for example, client/docs changes or proven test-only backend changes). Do not auto-add labels. If impact is uncertain, omit it and keep normal rollout.
- This is a discretionary review policy, not a code-enforced path allowlist. Do not use the label to bypass necessary rollout, required CI or provenance/security gates. Manual current-main rollout remains available; see [release behavior](docs/approved-main-releases.md#no-rollout-needed).

## Backward compatibility with shipped API clients

- Make best-effort backward compatibility a release requirement for the current API-only product. Gateway updates should preserve older shipped clients' authentication, model discovery, request submission, streaming, receipts and useful diagnostics without requiring a simultaneous client upgrade. This does not restore retired browser routes or promise indefinite support for every version.
- Assess compatibility from the old client's actual behavior, not just the new schema. An additive optional field, nullable value, different SSE grouping, header/trailer or changed settlement meaning can break a strict decoder. New-client tests against the new gateway alone are insufficient.
- Before changing a client-visible contract, identify the affected shipped versions and exercise the candidate gateway with the previously shipped client artifact or its exact pinned decoder, alongside the current client. Use offline/synthetic fixtures for authentication/catalog validation, quotes and reservations, stream ordering/terminal evidence, partial/final receipts and errors as applicable. Include regression tests for the old-client failure being prevented; record tested versions, coverage and unknowns. If an old artifact cannot be reproduced, disclose the gap rather than claiming compatibility. Live or paid probes still require separate authorization.
- Prefer preserving the existing default wire contract and exposing incompatible extensions through explicit capability negotiation, opt-in behavior or versioning when needed. Do not assume older clients ignore unknown fields. Use the smallest compatibility change that works; do not introduce speculative compatibility frameworks or duplicate provider SDK parsing.
- Never weaken attestation, endpoint binding, catalog/quote validation, reservation/settlement integrity, authenticated completion/tool gates or privacy restrictions to keep an old client working. Do not silently reinterpret partial settlement as success, omit necessary billing evidence, substitute models or replay uncertain inference. Clients may ignore only explicitly non-authorizing metadata, not unknown security/accounting semantics.
- If a breaking change is unavoidable, stop for explicit operator approval before merge/deployment. Document the affected versions, reason, compatibility-test evidence or gaps, actionable content-free upgrade diagnostics and a staged rollout/rollback plan. Qualify the matching client and arrange separately authorized installation and user-controlled activation before switching the gateway contract, or retain a safe old-client path during the transition; do not count a scratch build as installed or activated. Report known incompatibilities and remaining deployment limits rather than promising compatibility.

## Security model

Preserve these trust boundaries:

- The gateway and Tinfoil inference service see prompt plaintext in memory. The store and telemetry pipeline must never receive prompts or responses.
- The store is outside the attested boundary. It can associate payments with accounts and observes reservation/settlement events. Do not describe it as anonymous, invisible, or hardware-verifiable.
- Attestation proves a measured code/configuration identity; it does not prove that retention is impossible under runtime compromise, that the operator cannot change an unattested service, or that traffic cannot be correlated.
- Open egress, payment metadata, timing, account reuse, backups/WAL, inference caches, live catalog changes, and compromised dependencies are explicit residual risks.
- Production must fail closed before sending a prompt when attestation, release provenance, endpoint-key binding, model-catalog authentication/validation, or cost reservation fails.
- Never expose a usable credential in an image, repository, URL, metric, log, trace, panic, error body, or support artifact.  Compare authentication material in constant time where applicable.
- Treat all prompt text, submitted history, Markdown, model output, headers, payment callbacks, catalog responses, and upstream errors as hostile input. Bound parsing and memory at the transport layer; verify webhook signatures and replay resistance where payments are later implemented. Client-owned rendering is outside gateway scope.
- Idempotency, reservations, settlement, refunds, cancellation, retries, concurrency, and crash recovery are security/accounting behavior. Test their failure modes. Operator-approved Tinfoil-aligned streaming policy: an observed downstream client disconnect promptly closes the upstream operation; temporary delivery backpressure is not itself a client disconnect. Settle once at the submitted quote from validated authenticated final usage on successful completion, or trustworthy cumulative running usage on interruption, capped by the original reservation. Release the unused reservation; refund fully when no trustworthy billable usage exists. Model rejection or failure before a response begins is not billable. Never sum cumulative snapshots or infer billable usage from emitted text. Partial settlement is not successful completion or tool-execution authorization. Closing a connection does not establish immediate upstream compute termination or exact invoice parity; the operator absorbs unobserved upstream usage. Preserve the existing pre-request reservation and disclosed 30% markup, rather than adopting Tinfoil's soft credit limits. The gateway never automatically replays an uncertain generation. The current operator-approved [Pi client failure policy](docs/pi-client-failure-policy.md) supersedes native transient generation retries in the client source candidate: non-trust failures stop gracefully with warnings and no automatic inference retry/replay; ordinary user steering/follow-up remains native and each deliberate new submission may incur another charge. Fatal client turns/blocked dispatch are reserved for unconfirmed backend identity/authenticity; gateway HTTP/accounting outcomes are unchanged. Do not claim receipt is guaranteed. Upstream transport/resource failures remain errors, not a special post-disconnect grace-period cutoff.
- Disable local SDK prompt-cache persistence and unintended persistence explicitly. The operator-authorized session-scoped design permits upstream volatile prefix reuse through an independently random, memory-only 32-byte API-session secret, supplied only over verified inference. Never derive it from account/credential material or expose it in telemetry, diagnostics, URLs or support artifacts. Conversation resets retain the scope; separate logins/restarts do not share it. Session removal is not proof of upstream erasure, and accepted detached work retains its scope without changing the current disconnect/cumulative-usage policy. See `docs/prompt-caching-plan.md` for correlation/retention limits and source-only evidence. Use read-only roots and memory-only writable storage where the platform permits it. The separately authorized Pi public-evidence cache may retain public AMD VCEK DER including its embedded gateway hardware ID; this narrow public-certificate exception does not permit bare chip IDs, raw reports, full KDS URLs, cached verdicts or private data, nor telemetry/log/support export. See `PRIVACY.md` and `docs/pi-public-evidence-cache-plan.md`.

## User-facing error policy

- Follow the operator-approved [Pi client failure policy](docs/pi-client-failure-policy.md) for client turn/session behavior: warning-only graceful host stops except for backend identity/authenticity failure. Do not describe host `done/stop` as successful generation or settlement, and suppress provisional tools on incomplete/failed delivery. This does not change gateway outcomes.
- Because production does not export request logs or request-level traces, user-facing errors/warnings must be useful diagnostics: short, specific and actionable, not just “failed” or “invalid stream.”
- Preserve a stable, content-free error code and the failing stage/constraint across SDK, gateway and client boundaries. Distinguish request encoding, verified transport, SDK decoding, gateway validation, missing terminal usage/finish and settlement failures. Do not collapse known causes into one generic error.
- State billing/reservation status only from observed accounting or an authenticated terminal receipt. Otherwise say it is unknown. Never imply cancellation, refund or safe retry merely because delivery failed; say when the request was not replayed and warn that a new request may incur another charge.
- Use closed error categories and locally authored messages. Never display or retain raw SDK/upstream/parser errors, offending values, prompts, responses, history, credentials, headers, URLs, account identifiers or panic payloads. Rich diagnostics are not permission to echo hostile input.
- Show detailed errors transiently to the affected user; do not automatically log, trace, export or package them into support artifacts. Users may manually share the content-free error code for support, never credentials or request data. Aggregate observability remains governed by the telemetry policy below.
- Test both usefulness and privacy: each known failure keeps its category through the API/client boundary; hostile error text cannot escape; interrupted error delivery cannot fabricate a confirmed billing outcome. Diagnostics must not themselves initiate inference. The current Pi source policy does not retry inference from warnings; preserve unknown billing and disclose that a deliberate new submission may incur another charge. Native Pi/T3 history persistence is a separate boundary from transient notifications.

## Typed interface failures and minimal expected errors

- Every project-controlled external-facing boundary (inbound/outbound, including supporting startup/background/cleanup paths) must preserve a stable typed failure, known stage/constraint, locally authored action and evidence-supported outcome. Use existing enums and supported SDK error types; never classify formatted exception text. Unexpected faults require stage-specific cause-unknown fallbacks, even with telemetry off.
- Keep the smallest sufficient expected-error set; remove only proven redundant validation. Do not collapse known trust/accounting constraints, invent errors for normal duplicates/cancellation/shutdown, hide failures or weaken security/parser/accounting gates. Preserve a known primary failure and observed accounting outcome across subsequent delivery/cleanup faults. No new retries or inference from diagnostics.
- Record failures once at their sole operation owner, not at every wrapper. Only the reviewed closed projection may enter complete five-minute aggregate error metrics; no logs/traces/raw errors/dynamic codes. Withhold unqualified coverage rather than emit healthy zeros. Preserve shipped-client wire compatibility and disclose SDK/host interception limits.
- Follow [the policy extension](PRIVACY.md#typed-interface-failures-and-token-aggregate-extension) and [the implementation plan](docs/interface-error-token-metrics-plan.md). This policy is not implementation, export or deployment evidence and authorizes no client telemetry uploads, Pi/T3 host changes or future intake adapter.

## Telemetry policy

**Always read and reference [`PRIVACY.md`](PRIVACY.md) before touching telemetry**, including instrumentation, logs/traces, metrics, SDK defaults, collectors, resource discovery, dashboards, alerts, deployment, or diagnostic/support tooling. Link the applicable policy sections and privacy-test evidence in the change description and verification record. The policy applies to real data in testing as well as production; an environment label does not relax it. The rollout plan is [`docs/telemetry-plan.md`](docs/telemetry-plan.md). The operator's 2026-10-08 MVP decision permits deployment to the existing production gateway and Honeycomb's default retention. Direct authenticated Honeycomb US OTLP HTTPS (no Collector) and enablement with valid allowlisted credentials are now selected; `OTEL_SDK_DISABLED=true` is the off switch. Other privacy/runtime gates still apply. A development telemetry destination does not make production traffic synthetic.

Production request observability uses aggregate Honeycomb metrics only. The [startup-only exception](PRIVACY.md#startup-diagnostics-exception) additionally permits finite closed platform/Honeycomb startup logs and lifecycle counts in the normal destination, not a separate dataset:

- Sanitize and aggregate locally before direct authenticated TLS export; enforce the final allowlist in-process, without a Collector.
- Send sanitized aggregates to Honeycomb US with provider-default retention for the MVP, per the explicit operator decision in `PRIVACY.md`. Record effective retention when verified; request shorter retention (target: seven days) after the MVP. Do not claim that the default is seven days.
- Do not export production request logs or request-level traces. Startup-only logs must follow the closed schema/lifecycle in the exception above; no raw exceptions, private config, credentials, identifiers or request data. Do not add a logging bridge or tracing framework.
- Never export prompts, responses, conversation history, request bodies, URLs/query strings, headers, client IPs, user agents, credentials, account/payment identifiers, onion identifiers, stable pseudonyms, exact request timestamps, or per-request token/cost events.
- Allowed signals are low-cardinality aggregates such as coarse request counts, status classes, latency buckets, queue depth, and process health, subject to the privacy-release gates in `PRIVACY.md`. The subsequent operator-requested [error/token extension](PRIVACY.md#typed-interface-failures-and-token-aggregate-extension) permits complete five-minute typed failure counts and observed input/output/cached-input token sums through the existing reviewed model partitions, including validated `other`; query-sum partitions for across-model totals rather than export overlapping marginals. Count validated final or last trustworthy cumulative usage once, never snapshots/estimates; cached input is a subset and unknown cache evidence is not zero. Cost metrics remain excluded. This is policy/planning approval, not implementation or activation evidence. Never export user- or session-keyed aggregates. Apply the operator-approved 2026-10-09 complete five-minute aggregate policy, without minimum-count or linked-sparsity suppression. Preserve complete-window and lifecycle/arithmetic integrity gates. Sparse aggregates may reveal individual activity; neither bucketing nor observation counts establish anonymity or prevent external timing correlation.
- Sampling is not sanitization. Do not rely on vendor-side deletion as the primary control.
- Restrict access, document Honeycomb as a third-party processor, and provide a kill switch. Core service behavior must work with telemetry disabled.
- Do not claim “no telemetry” or “no logs whatsoever.” Claim only that request content and identifying/request-level telemetry are not collected, within the tested configuration.

## Verification discipline

- Convert privacy claims into scoped, testable statements with assumptions and live-phase labels.
- Add negative tests for sensitive-field export, hostile API input, oversized transport input, duplicate submissions, reservation races, retries, disconnects, upstream failures, and crash recovery.
- Verify actual runtime behavior and generated artifacts; configuration intent alone is not evidence.
- Record unresolved platform properties as unknowns rather than guarantees.
